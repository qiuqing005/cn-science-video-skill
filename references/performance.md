# 快速模式

目标是减少等待和重复推理，同时保留一次完整成片验收。适用于用户没有要求逐镜头审批、成片不超过约 3 分钟的任务。

## 已验证基线

在一台 12GB NVIDIA GPU 的实测中，Qwen3-TTS 1.7B 对四段、约 99 秒普通话旁白逐段串行生成耗时 227 秒；改为一次四段批处理后耗时 64 秒，峰值显存约 6.7GB。该数据只用于选择策略，不应当作其他设备的保证值。

## 执行预算

- 收到剧本后一次完成分段、检索词、字幕摘要和场景模板选择，不再单独写重复的 storyboard 文案。
- 120 秒以内默认 4-6 个场景；每段只选择一个主素材和一个原创图解 fallback。
- 每个素材检索最多 20 秒、两个来源、一次失败重试。超过预算立即使用原创图解。
- 优先复用同工作区已冻结且许可可追溯的素材、字体、GSAP 和 HyperFrames 包装器。
- 主流程只写场景 JSON；优先让已有模板生成 HTML。不要在每个项目中重新创造 CSS 体系、时间线框架和验收脚本。
- `lint` 先单独运行；通过后并行执行 `validate`、严格模式 `inspect` 和需要更新的中点 contact sheet。视觉正常后直接执行一次高质量渲染。
- 不进行“为了保险”的重复全量检查。修复局部错误后只重跑失败门禁；渲染成功后执行 `ffprobe`、响度、黑帧和最终 contact sheet。
- 已通过的严格组合门禁和最终媒体门禁分别使用依赖时间与 MP4 SHA-256 复用；未变化项目不重复启动 Chrome 或完整解码成片。

## 批量 TTS

Qwen3-TTS 使用 `scripts/qwen_batch_tts.py`。脚本按可用显存自动选择批大小：大显存优先 4 段一批，中等显存 2 段一批，低显存逐段；显存不足时自动二分重试。生成结果在写入前统一用 FFmpeg `atempo` 处理到目标速度。

已知剧本文字的本地 TTS 使用 `scripts/align_captions.py` 做快速对齐。清晰 TTS 可先用 Whisper `base`；噪声较多或边界不稳定时再升到 `small`。不要把 Whisper 识别出的错词直接显示在字幕中，使用其时间戳映射回原始剧本。

不要在同一张 GPU 上启动多个独立模型进程。批处理共享一次模型加载和一次生成循环，比多进程争抢显存更快、更稳定。连续制作多部视频时可以保留一个模型服务进程，避免重复加载权重。

## 减少渲染时间

1. TTS 输出先用 `atempo=1.2` 保持音高并加速。
2. 库存视频在标准化转码时同时使用 `setpts=PTS/1.2`；原创动画直接按加速后的时间线编排。
3. 使用处理后音频的真实时长生成根 `data-duration`，因此 HyperFrames 只渲染最终需要的帧数。
4. 渲染后仅复制视频流并对音频做全片 `loudnorm`，不再执行一次完整 NVENC/CPU 视频重编码。
5. 先执行本地 NVENC 单帧冒烟测试；通过后使用 HyperFrames `--gpu`，失败自动回退 CPU。显式 worker 数可跳过自动校准，但必须按 CPU 和内存限制，默认不超过 6。

在 RTX 5070、16 逻辑 CPU 的同一部 89.6 秒 1080p/30fps 成片上，`high + auto workers + CPU encode` 渲染为 94.8 秒；`high + 6 workers + GPU encode` 为约 80–81 秒。两者逐帧 SSIM 为 0.99874。该结果只用于本机策略选择，不保证其他硬件获得相同比例收益。

同一项目在严格组合门禁与最终媒体哈希均命中时，完整断点续跑实测为 0.054 秒；首次建立成功标记仍会执行真实检查，不能把该数字理解为冷启动生成时间。

## 字体

HyperFrames 会把本地字体嵌入编译结果。十几 MB 的完整中文字体可能单独增加数十秒编译时间。生成 HTML 后收集片中实际字符，使用 `scripts/subset_font.py` 和工作区虚拟环境里的 FontTools 创建字体子集，输出到 `assets/fonts/`；保留 ASCII、数字、标点和剧本中的全部汉字。子集化后必须重新运行 `validate` 和快照，确认没有缺字。

## 预期路径

对 60-90 秒视频，在已存在模型、模板和媒体缓存的机器上，合理目标是：TTS 与素材并行 1-2 分钟，模板组装与检查 30-60 秒，渲染 1-2 分钟，总计约 3-5 分钟。首次下载模型、缺少素材缓存或需要大量定制图解时不承诺该范围。
